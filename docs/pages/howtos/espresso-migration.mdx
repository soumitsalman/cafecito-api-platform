# Migrating to Espresso from Event and News APIs

This guide compares Espresso with the GDELT Cloud, PredictHQ, and Perigon route families documented in `INDUSTRY_EVENT_API_ROUTE_REFERENCE.md`. It is migration guidance, not a promise that Espresso is a drop-in replacement.

Espresso answers a different product question from an article API:

> Beans finds and verifies what publishers published. Espresso explains what happened and what it may mean.

Use Espresso for structured Events, higher-level Signals, bounded provenance traversal, and agent-oriented output. Use Beans or the original provider when you need article bodies, publisher citations, canonical place/entity profiles, or provider-specific event metrics.

## At-a-glance comparison

| Capability | GDELT Cloud | PredictHQ | Perigon | Espresso |
| --- | --- | --- | --- | --- |
| Primary object | Normalized Event and Story | Predicted/observed Event | Article, Story, vector result | Event and derived Signal |
| Pagination | `limit`, `cursor`, `next_cursor` | `limit`, `offset`, `next` | zero-based `page`, `size` | `limit`, opaque `page`, `next_page` |
| Page count | Usually omitted | `count` is total matches | `numResults` is total matches | `pagination.num_results` is current-page count; no separate total |
| Search | `search` | `q` | `q` or vector prompt | `q` on supported Event/Signal collections |
| Time | `date_start`, `date_end` | lifecycle/start/end families | publication and ingestion ranges | date-only `from`/`to` bound `created_at` |
| Classification | family/category/subcategory | category/label/taxonomy | category/topic/taxonomy/label | exact `event_types` and separate exact `categories`; no hierarchy |
| Entities | canonical entity references | `entity.id` and embedded entities | people/company enrichment | exact normalized company/people names via `entities`, `companies`, `people` |
| Geography | country/region/admin1/coordinates | places and geometry | country/city/coordinates | exact normalized `regions`; no structured geography |
| Source filter | domain | source context | source/domain/group/paywall | discover Source UUIDs, then use `source_ids` |
| Output | JSON with provider envelope | JSON with `results` and counts | JSON with `articles`/`results` and status | JSON, YAML, or TOON; YAML/TOON are token-optimized for MCP and AI agents |

## Query-parameter migration

### From GDELT Cloud

| GDELT concept | Espresso mapping | Migration note |
| --- | --- | --- |
| `date_start`, `date_end` | `from`, `to` | Use ISO date-only values. Espresso bounds record `created_at`, not Event occurrence time. |
| `event_family`, `category`, `subcategory` | `event_types`, separate `categories` | Espresso does not expose a family/subcategory hierarchy. Do not treat `categories` as an alias for `event_types`. |
| `country`, `region`, `continent`, `admin1` | `regions` | Values are exact normalized names, not country codes or coordinate queries. |
| `domain` | `GET /sources?domains=...` then `source_ids` | Source filtering is UUID-based on Event routes. |
| `search` | `q` | Semantic query is available on supported collection routes; relation collections do not expose semantic `q` in V1. |
| `limit`, `cursor` | `limit`, `page` | Do not decode or construct Espresso page tokens. |
| `next_cursor` | `pagination.next_page` | Send it back as the next request’s `page`. |
| `summary`/story/article references | Event detail/evidence/Signal links | Espresso returns structured records and relation routes, not GDELT article bundles. |

Example translation:

```text
GDELT: /api/v2/events?date_start=2026-05-01&date_end=2026-05-31&category=politics&limit=20&cursor=...
Espresso: /espresso/events?from=2026-05-01&to=2026-05-31&categories=regulation&limit=20&page=...
```

### From PredictHQ

| PredictHQ concept | Espresso mapping | Migration note |
| --- | --- | --- |
| `q` | `q` | Keep natural-language search where the Espresso route supports it. |
| `id` | `ids` or `/{event_id}` | Use `ids` for a collection constraint or the detail route for one Event. |
| `category`, `label`, `phq_label` | `event_types`, separate `categories`, or fuzzy `tags` | Choose the Espresso dimension deliberately; there is no shared taxonomy hierarchy. |
| `entity.id` | `entities`, `companies`, or `people` | Espresso matches exact normalized names, not canonical entity IDs. |
| `country`, `place.*`, `within` | `regions` | Exact region strings only; no place database, radius, or coordinates. |
| `start.*`, `end.*`, `active.*`, `updated.*`, `cancelled.*` | `from`, `to` | Only record creation bounds are published in Espresso V1. |
| `rank`, attendance, spend, impact metrics | no V1 equivalent | Preserve provider-specific analytics in the source system. `impact_levels` is categorical, not a numeric rank. |
| `limit`, `offset`, `next` | `limit`, `page`, `pagination.next_page` | Replace offset loops with opaque page-token loops. |
| `/v1/events/count/` | no V1 equivalent | Aggregate count routes remain deferred. |

Example translation:

```text
PredictHQ: /v1/events/?q=semiconductor&category=concerts&limit=10&offset=20
Espresso:  /espresso/events?q=semiconductor&event_types=market_entry&limit=10&page=...
```

### From Perigon

| Perigon concept | Espresso mapping | Migration note |
| --- | --- | --- |
| `/v1/articles/all` | `GET /events` | Map article search to structured Event search only when the application wants normalized developments rather than article records. |
| `/v1/stories/all` | `GET /events` or `GET /signals` | There is no generic Story object. Use Events for developments and Signals for synthesized conclusions. |
| `/v1/vector/news/all` | `q` on supported collections | The target POST Event vector route is deferred; use collection `q` where available. |
| `category`, `topic`, `taxonomy`, `label` | `categories`, `event_types`, or `tags` | Categories and Event types are separate exact fields; tags are fuzzy text matching. |
| `source`, `sourceGroup`, `domain`, `paywall` | `/sources` then `source_ids` | Espresso does not expose source-group or paywall filters on Events. |
| `from`, `to`, `addDate*`, `refreshDate*` | `from`, `to` | Only `created_at` is bounded in V1. |
| `page`, `size` | `page`, `limit` | Espresso page tokens are opaque and `limit` is 1–100. |
| `sortBy` | no V1 equivalent | Do not silently translate provider ordering into an undocumented Espresso sort. |
| article `summary`, `title`, `url` | Event `summary`, detail `url` | Collection payloads intentionally omit provenance fields; no stable title is promised. |
| article/story history | Event evidence and Signal links | These are resource-oriented traversals, not article revision history. |

Example translation:

```text
Perigon: /v1/articles/all?q=chip+shortage&category=technology&page=2&size=20
Espresso: /espresso/events?q=chip+shortage&categories=technology&page=...
```

## Response and envelope migration

| Provider shape | Espresso shape | What changes in client code |
| --- | --- | --- |
| GDELT `success`, `data`, `pagination.next_cursor` | HTTP 2xx, `data`, `pagination.next_page` | Remove body-level success checks; loop on `next_page`. |
| PredictHQ `count`, `results`, `next` URL | `data`, `pagination.num_results`, `pagination.next_page` | Treat `num_results` as current-page count; do not assume a total-match count or URL continuation. |
| Perigon `status`, `numResults`, `articles`/`results` | HTTP 2xx, `data`, `pagination.num_results` | Use `data` for both Event and Signal collections; no body status field. |
| Provider title/description | `summary` | Expect a normalized narrative, not a stable title or article body. |
| Provider publication/start/lifecycle timestamps | `created_at` | Treat the timestamp as record creation time only. |
| Canonical entities/places | Exact string arrays and names | Do not expect IDs, profiles, country codes, coordinates, or aliases. |
| Provider source objects | `source_id`/`source` on details | Collection provenance can be omitted or unavailable; do not fabricate it. |

A collection response is always an envelope:

```json
{
  "data": [],
  "pagination": {
    "limit": 20,
    "num_results": 0,
    "page": null,
    "next_page": null
  },
  "meta": {"as_of": "2026-08-14T00:00:00Z"}
}
```

## Espresso capabilities without direct provider equivalents

Migration is not only field renaming. Espresso adds workflow primitives that are not equivalent to a provider article, story, or predicted-event route:

- **First-class Signals** — a distinct resource for synthesized conclusions, with a detail route and supporting-Event traversal.
- **Question-oriented evidence** — `GET /events/{event_id}/evidence` expresses source coverage without requiring clients to understand `SAME_AS` edges or graph direction. The default scope is direct related evidence, not an unbounded transitive closure.
- **Bidirectional resource traversal** — Event → Signals and Signal → supporting Events are named by the resource the user wants, hiding `DERIVED_FROM` storage orientation.
- **Source discovery and citation context** — `/sources` provides a stable UUID that can be reused as an Event filter, while nullable metadata is represented honestly.
- **Filter discovery** — `/tags`, `/event-types`, `/entities`, and `/regions` make exact values and fuzzy tag vocabulary discoverable.
- **Token-optimized output** — YAML and TOON preserve the canonical payload for MCP and AI-agent consumption without introducing a second data contract.

## Migration checklist

1. Decide whether the target workflow needs structured intelligence or publisher articles/full text. Use Beans or the original provider for article-level requirements.
2. Replace provider pagination with `limit` plus opaque Espresso `page`/`next_page` handling.
3. Translate dates to `from`/`to` only when record-creation time is an acceptable substitute.
4. Map taxonomy filters deliberately: `event_types` and `categories` are separate exact fields; `tags` are fuzzy text matching.
5. Replace canonical entity/place IDs with exact normalized names only when the application can tolerate string-based matching.
6. Add a Source discovery step before using Event `source_ids`.
7. Update clients to read `data`, `pagination`, `meta`, and detail-only provenance fields.
8. Use JSON for canonical integrations; use YAML or TOON for token-constrained MCP/agent workflows.
9. Keep unsupported provider features explicit instead of silently dropping them: lifecycle windows, coordinates, total counts, numeric metrics, article bodies, and generic Story objects are not Espresso V1 features.
