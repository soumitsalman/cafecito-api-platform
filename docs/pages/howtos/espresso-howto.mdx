# Espresso API & MCP

<Badge variant="default">v1</Badge><Badge className="badge-live">Live</Badge>

Espresso is a business-intelligence API:

- **Events** are concrete intelligence records with market intelligence fields.
- **Signals** are higher-level conclusions derived from Events.

Every record ID is an RFC 4122 UUID. Collections return a stable `data` / `pagination` / `meta` envelope; detail routes return `data`.

## Key features

- **Structured intelligence records** — Query Event developments and Signal conclusions with stable UUIDs, creation timestamps, flattened intelligence fields, and optional Source provenance.
- **Semantic retrieval** — Use natural-language `q` on supported Event and Signal collection routes; use `from` and `to` to bound record creation time.
- **Precise and tolerant filters** — `event_types`, `categories`, `entities`, `impact_levels`, `companies`, `people`, `products`, and `regions` use exact normalized names; `tags` use fuzzy text matching.
- **Question-oriented traversal** — Follow Event evidence and Signal-support routes without learning `SAME_AS` or `DERIVED_FROM` storage direction; evidence remains a bounded direct-related-record view.
- **Discoverable provenance** — Use Source and filter-vocabulary routes to make citations and exact filters understandable; unavailable metadata remains omitted or null.
- **Agent-ready representations** — JSON is canonical, while YAML and TOON are token-optimized for MCP and AI-agent clients. The hosted MCP endpoint exposes the same REST operations.

## Output formats for applications, MCP, and agents

`response_type=json` is the canonical format. `response_type=yaml` and `response_type=toon` serialize the same payload for token-optimized use by MCP clients and AI agents. The formats do not change filtering or pagination.

```bash
curl -s "${BASE_URL}/espresso/events?limit=2&response_type=yaml" \
  -H "Authorization: Bearer ${API_KEY}"
```

The same request with `response_type=toon` is useful when an MCP tool needs compact, regular records. Use JSON when your application needs the canonical machine-readable contract.

## Hosted MCP endpoint

MCP-compatible clients can connect to `https://api.cafecito.tech/espresso/mcp` with the same API key. The hosted tools are generated from the REST operations and use the same Event, Signal, Source, discovery, pagination, and `response_type` contract described here.

## Common collection parameters

| Parameter | Meaning |
| --- | --- |
| `limit` | Number of records requested per page; integer from 1 to 100, default 20. |
| `page` | Opaque page token. Do not construct or inspect it. |
| `response_type` | `json` (canonical), `yaml`, or `toon` (token-optimized for MCP and AI agents). |
| `from` / `to` | Inclusive ISO date-only bounds on `created_at`; they are not occurrence or publication dates. |
| `q` | Optional semantic query where the route supports it. Source/discovery `q` values are text matching, not semantic search. |

When a collection includes a non-null `pagination.next_page`, pass it back as the next request's `page` value. Do not use offsets or treat `next_page` as a sortable value.

## Filter matching

Espresso uses two matching modes:

| Filter | Matching behavior | Example values |
| --- | --- | --- |
| `tags` | Fuzzy text matching against persisted tag labels. | `policy,supply_chain` |
| `event_types` | Exact Event type names after snake_case normalization. | `policy_change,market_entry` |
| `categories` | Exact category names after snake_case normalization; this is a separate field from `event_types`. | `regulation,technology` |
| `entities` | Exact company or people names after snake_case normalization. | `microsoft,nvidia` |
| `impact_levels` | Exact impact-level names. | `high,medium,low` |
| `companies` | Exact company names after snake_case normalization. | `microsoft,nvidia` |
| `people` | Exact person names after snake_case normalization. | `sam_altman,elon_musk` |
| `products` | Exact product names after snake_case normalization. | `windows,geforce` |
| `regions` | Exact region names after snake_case normalization. | `north_america,europe` |
| `impacted_domains` | Exact impacted-domain names after snake_case normalization on Signal routes. | `public_health,climate` |

Use the discovery routes to find the public names accepted by exact filters; examples use user-facing snake_case names.

A collection response looks like this:

```json
{
  "data": [
    {
      "id": "339366bc-464d-582f-8132-6875ccc814d2",
      "created_at": "2026-05-19T06:00:00Z",
      "kind": "event",
      "event_type": "policy_change",
      "summary": "A policy change affects regional suppliers.",
      "tags": ["policy", "supply-chain"]
    }
  ],
  "pagination": {
    "limit": 20,
    "num_results": 1,
    "page": null,
    "next_page": null
  },
  "meta": {"as_of": "2026-08-14T00:00:00Z"}
}
```

The same collection in YAML is useful for a token-conscious MCP or AI-agent exchange:

```yaml
data:
  - id: 339366bc-464d-582f-8132-6875ccc814d2
    created_at: 2026-05-19T06:00:00Z
    kind: event
    event_type: policy_change
    summary: A policy change affects regional suppliers.
pagination:
  limit: 20
  num_results: 1
  page: null
  next_page: null
meta:
  as_of: 2026-08-14T00:00:00Z
```

`num_results` is the number of records returned in the current page; `data.length` is the portable way to count those records. Espresso does not return a separate total-match count. Empty collections still return HTTP 200 with `data: []`.

## Discover values before filtering

Discovery routes return public filter names in normalized snake_case where applicable, not canonical entity profiles or a geography hierarchy. Tag discovery returns labels for fuzzy matching.

| Route | Use |
| --- | --- |
| `GET /espresso/tags` | Discover persisted Event and Signal tag values. Use `resource=event` or `resource=signal`. |
| `GET /espresso/event-types` | Discover exact Event type names in snake_case. |
| `GET /espresso/entities` | Discover exact company and people names in snake_case. `types` accepts `company,people`. |
| `GET /espresso/regions` | Discover exact region names in snake_case. |

Example:

```bash
curl -s "${BASE_URL}/espresso/event-types?limit=20" \
  -H "Authorization: Bearer ${API_KEY}"
```

Use a returned value with the matching filter: `event_types`, the separate `categories` field, `entities`, `tags`, or `regions` on the relevant Event route.

## Find Events by date, tags, and entities

`GET /espresso/events` supports Event IDs, exact snake_case `event_types`, exact snake_case `categories` as a separate field, exact `entities` matching against company or people names, exact `impact_levels`, `companies`, `people`, `products`, and `regions`, direct `source_ids`, fuzzy `tags`, and optional semantic `q`.

```bash
curl -s --get "${BASE_URL}/espresso/events" \
  -H "Authorization: Bearer ${API_KEY}" \
  --data-urlencode "from=2026-05-01" \
  --data-urlencode "to=2026-05-31" \
  --data-urlencode "tags=policy,supply_chain" \
  --data-urlencode "entities=microsoft,nvidia" \
  --data-urlencode "event_types=policy_change" \
  --data-urlencode "categories=regulation" \
  --data-urlencode "limit=20"
```

Tags use fuzzy text matching against persisted tag labels. Structured filters use exact matching after snake_case normalization. `categories` targets the Event category field and is independent from `event_types`; `entities` targets exact names in either the Event `companies` or `people` values. Filters do not resolve aliases or entity IDs.

For a second page, copy the opaque token exactly:

```bash
curl -s --get "${BASE_URL}/espresso/events" \
  -H "Authorization: Bearer ${API_KEY}" \
  --data-urlencode "page=OPAQUE_VALUE_FROM_pagination.next_page"
```

## Inspect an Event, its evidence, and derived Signals

### Event detail

```bash
curl -s "${BASE_URL}/espresso/events/339366bc-464d-582f-8132-6875ccc814d2" \
  -H "Authorization: Bearer ${API_KEY}"
```

Event detail adds usable provenance (`source_id`, `source`, `url`, and `base_url` when present), relation links, and relation counts. A missing Source reference is represented by omitted or null optional fields; the API does not invent Source metadata.

### Evidence trail

```bash
curl -s --get "${BASE_URL}/espresso/events/339366bc-464d-582f-8132-6875ccc814d2/evidence" \
  -H "Authorization: Bearer ${API_KEY}" \
  --data-urlencode "source_ids=a1b2c3d4-e5f6-7890-abcd-ef1234567890"
```

Evidence is a collection envelope whose current V1 items expose `id`, `kind`, `created_at`, `tags`, `source_id`, `url`, and `base_url`. It is a compact evidence-trail view for source coverage, not article content or story membership. Use `ids` to restrict returned Event records when needed.

### Signals derived from an Event

```bash
curl -s "${BASE_URL}/espresso/events/339366bc-464d-582f-8132-6875ccc814d2/signals?limit=20" \
  -H "Authorization: Bearer ${API_KEY}"
```

This relation route returns Signals derived from the Event's evidence trail. It accepts Signal `ids`, `impact_levels`, `impacted_domains`, tags, date bounds, and the common pagination/serialization parameters. It does not expose Signal `source_ids` or relation-level semantic `q` in V1.

## Search Signals and inspect supporting Events

```bash
curl -s --get "${BASE_URL}/espresso/signals" \
  -H "Authorization: Bearer ${API_KEY}" \
  --data-urlencode "q=regional supply pressure" \
  --data-urlencode "from=2026-05-01" \
  --data-urlencode "impact_levels=high" \
  --data-urlencode "limit=20"
```

Signal collections expose flattened Signal fields and omit collection-level provenance. Retrieve a Signal for its usable Source metadata, relation links, and counts:

```bash
curl -s "${BASE_URL}/espresso/signals/SIGNAL_UUID" \
  -H "Authorization: Bearer ${API_KEY}"
```

Then inspect the Events used to derive it:

```bash
curl -s --get "${BASE_URL}/espresso/signals/SIGNAL_UUID/events" \
  -H "Authorization: Bearer ${API_KEY}" \
  --data-urlencode "categories=regulation" \
  --data-urlencode "entities=microsoft" \
  --data-urlencode "limit=20"
```

`GET /signals/{signal_id}/events` supports Event IDs, exact `event_types`, the separate exact `categories` field, exact company/people/product/region names, exact `entities`, exact impact levels, direct source IDs, fuzzy tags, date bounds, and page pagination. It returns Events that support the Signal's conclusion.

## Sources

Find a Source by metadata, then use its UUID as an Event filter:

```bash
curl -s --get "${BASE_URL}/espresso/sources" \
  -H "Authorization: Bearer ${API_KEY}" \
  --data-urlencode "q=example.com" \
  --data-urlencode "domains=example.com"

curl -s "${BASE_URL}/espresso/sources/SOURCE_UUID" \
  -H "Authorization: Bearer ${API_KEY}"

curl -s "${BASE_URL}/espresso/events?source_ids=SOURCE_UUID" \
  -H "Authorization: Bearer ${API_KEY}"
```

Source payloads include `id`, `url`, `domain`, and `name`; `description`, `favicon_url`, and `rss_feed_url` are returned only when available.

## V1 boundaries

Espresso V1 does not publish Actions, Stories, article bodies, canonical entity profiles, structured places, lifecycle timestamps, numeric event metrics, aggregate count/summary routes, or the deferred POST Event vector-search route. `created_at` is record creation time. Some records have incomplete Source metadata or sentinel year-0001 timestamps; clients should treat those as data-quality signals rather than occurrence dates.
